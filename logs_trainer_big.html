📜 Как читать логи, когда их слишком много

⭐ Расширенный гайд по материалу Habr + диагностика по источникам ошибок, карта принятия решений, реальные кейсы и тесты.

🔍 Фильтр по источнику:

📖 1. Основы: уровни логирования и стратегия поиска

🎚️ Уровни важности (от INFO до FATAL)
  • INFO – штатная работа
  • DEBUG – детали для разработчика
  • WARN – возможная проблема
  • ERROR – ошибка, но сервис жив
  • FATAL/CRITICAL – критический сбой компонента
  • TRACE – слишком подробно (осторожно на проде)
🧠 С чего начинать разбор (правило 5 минут)
  1. Когда началась деградация?
  2. Где стала заметна? (nginx / app / БД)
  3. Какой компонент ближе к симптому?
  4. Какие журналы относятся к цепочке?
  5. Идём от симптома: nginx → app → БД → очередь → ОС

🎯 2. Диагностика по источникам ошибок

🐧 Ядро Linux / OOM Killer / segfault
# Просмотр сообщений ядра за последний час journalctl -k --since "1 hour ago" --no-pager # Фильтр по OOM Killer и убитым процессам journalctl -k | grep -Ei 'oom|killed process|out of memory' # Поиск segfault (ошибки сегментации) journalctl -k | grep -i 'segfault' # dmesg для аппаратных ошибок dmesg | tail -50 | grep -i 'error\|fail'
🗄️ PostgreSQL: медленные запросы, блокировки, ошибки
# Поиск ошибок и FATAL в логах grep -i 'ERROR\|FATAL\|PANIC' /var/log/postgresql/postgresql-*.log | tail -50 # Поиск медленных запросов grep 'duration' /var/log/postgresql/postgresql-*.log | awk '{print $NF, $0}' | sort -rn | head -20 # Активные блокировки из psql sudo -u postgres psql -c "SELECT * FROM pg_locks WHERE NOT granted;" # Активные транзакции sudo -u postgres psql -c "SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction';"
📁 MySQL: deadlock, timeout, медленные запросы
# Ошибки MySQL grep -i 'error\|deadlock\|timeout' /var/log/mysql/error.log # Медленные запросы (если включён slow-query log) mysqldumpslow /var/log/mysql/mysql-slow.log | head -10 # Текущие процессы (в MySQL) mysql -e "SHOW FULL PROCESSLIST;" # Информация о блокировках mysql -e "SHOW ENGINE INNODB STATUS\G" | grep -A20 'LATEST DETECTED DEADLOCK'
🌐 Nginx: 5xx, таймауты, прокси
# Ошибки nginx (5xx) awk '$9 >= 500' /var/log/nginx/access.log | cut -d' ' -f1,7,9 | sort | uniq -c | sort -nr | head -20 # Таймауты в error.log grep -i 'timeout\|upstream timed out' /var/log/nginx/error.log # Проверка конфигурации nginx -t # Статистика по status кодам awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -nr
🖥️ Приложение (Python/Node.js): stack trace, exception
# journalctl для systemd-сервиса journalctl -u myapp -n 200 --no-pager # Поиск stack trace с контекстом (50 строк после) grep -A50 'Traceback\|Exception\|Error' /var/log/myapp/app.log | head -200 # Поиск по request ID grep -Rni 'request_id=abc123' /var/log/myapp/
🔒 Безопасность: SSH, аутентификация, брутфорс
# Неудачные попытки входа по SSH grep 'Failed password' /var/log/auth.log | tail -50 # Топ IP с неудачными входами grep 'Failed password' /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr | head -10 # Подозрительная активность (sudo) grep 'sudo.*COMMAND' /var/log/auth.log | tail -30 # Windows: неудачные логины (Event ID 4625) Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4625; StartTime=(Get-Date).AddHours(-1)} | Format-List
💾 Диск и файловая система: место, I/O ошибки
# Свободное место df -h # I/O ошибки в ядре journalctl -k | grep -i 'i/o error\|no space left\|read-only' # inode usage (Linux) df -i # Windows: место на дисках Get-PSDrive -PSProvider FileSystem | Select Name, Used, Free
🌐 Сеть: таймауты, сбросы, DNS
# Открытые порты и соединения ss -tulpn # DNS проблемы в логах grep -i 'dns\|resolve' /var/log/syslog | tail -30 # Сбросы соединений (TCP RST) journalctl -k | grep -i 'reset' # Windows: сбросить TCP стек netsh int ip reset

🔍 4. Реальные кейсы: разбор ситуаций

📌 Кейс 1: Приложение падает с OOM Killer
Симптом: Процесс неожиданно завершается, в логах "Killed process".
Диагностика:
# 1. Проверяем, был ли OOM Killer journalctl -k | grep -i 'oom\|killed process' # 2. Смотрим память до/после free -h # 3. Кто потреблял память? (если есть логи до падения) cat /var/log/myapp/app.log | grep -B20 'Killed'
Решение: Увеличить RAM, настроить swap, ограничить память для приложения.
📌 Кейс 2: PostgreSQL не отвечает на запросы
Симптом: Таймауты соединений, запросы висят.
Диагностика:
# 1. Активные транзакции sudo -u postgres psql -c "SELECT pid, state, query FROM pg_stat_activity WHERE state = 'idle in transaction';" # 2. Поиск блокировок sudo -u postgres psql -c "SELECT * FROM pg_locks WHERE NOT granted;" # 3. Медленные запросы из логов grep 'duration' /var/log/postgresql/postgresql-*.log | tail -20
Решение: Завершить зависшие транзакции, оптимизировать запросы, настроить параметры БД.
📌 Кейс 3: Nginx возвращает 502 Bad Gateway
Симптом: Пользователи видят 502 ошибку.
Диагностика:
# 1. Логи nginx grep '502' /var/log/nginx/access.log | tail -20 # 2. Логи апстрима (приложение/BE) journalctl -u myapp --since "5 minutes ago" --no-pager | tail -30 # 3. Проверить, жив ли апстрим curl -I http://localhost:8000/health
Решение: Перезапустить апстрим, проверить конфиги nginx, увеличить таймауты.
📌 Кейс 4: Атака брутфорса по SSH
Симптом: Много неудачных логинов, сервер тормозит.
Диагностика:
# 1. Анализ auth.log grep 'Failed password' /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr | head -10 # 2. Блокировка IP sudo fail2ban-client status sshd
Решение: Настроить fail2ban, сменить SSH порт, ограничить доступ по ключам.

🛠️ 5. Лайфхаки и инструменты

🎯 Ограничивайте выборку до чтения
journalctl --since, --until, -u, -p, _PID
🔁 Считайте повторы
grep 'error' app.log | sort | uniq -c | sort -nr | head -20
📖 Контекст (-A, -B, -C)
grep -A20 -B10 'panic' app.log
🔄 Проверяйте ротацию (gz, старые экземпляры)
zgrep -i 'error' /var/log/myapp/*.gz
🧠 Сохраняйте ход расследования
Время симптома
Записывайте гипотезы
🔑 Добавляйте request ID / trace ID
grep -Rni 'request_id=abc123' /var/log/
